# 帖子回复楼中楼算法

本文记录帖子页面将 V2EX 平铺回复转换为楼中楼结构的当前规则、设计取舍和已知边界，方便后续排查展示结果及迭代父回复推断算法。

## 背景

V2EX 帖子页面返回的是按楼层排列的回复列表。回复数据包含回复 ID、作者、楼层和正文，但不包含可靠的父回复 ID。因此，楼中楼关系只能根据正文中的 `@用户名` 和 `#楼层` 进行启发式推断。

帖子页面保留原始平铺数组，初始使用楼中楼模式，并支持两种展示模式：

- 普通列表模式：严格按照 V2EX 返回顺序平铺展示
- 楼中楼模式：调用 `buildReplyTree()` 生成回复树后递归展示

切换模式只改变 Webview 的展示结构，不修改回复数据，也不会影响回复、感谢、链接导航和图片预览等操作。

## 代码位置

- 算法实现：`webview/src/topic/replyTree.ts`
- 页面渲染与模式切换：`webview/src/topic/TopicApp.tsx`
- 嵌套回复样式：`webview/src/topic/topic.scss`

## 输入与输出

`buildReplyTree()` 的输入是当前回复页的平铺 `TopicReply[]`，输出是带有 `children` 的根节点列表：

```ts
interface TopicReplyNode extends TopicReply {
  children: TopicReplyNode[]
}
```

算法只处理当前页数据。引用其他分页中的楼层时不会跨页加载或推断父回复。

## 引用提取

回复正文是 HTML。算法先通过 `<template>` 提取纯文本，再按书写顺序识别引用：

```text
@用户名
@用户名 #楼层
```

用户名当前使用 `[a-zA-Z0-9_-]+` 匹配，楼层使用数字匹配。

正常情况下，楼层紧跟在对应用户名之后，例如 `@alice #12`。如果正文中只有一个楼层号，算法会用它与全部被提及用户尝试精确作者匹配，以兼容楼层写在多个用户名末尾的格式：

```text
@alice @bob #12
```

如果第 12 楼作者是 `alice`，则匹配 `alice`；如果作者是 `bob`，则匹配 `bob`。楼层作者不属于任何被提及用户时，不会仅凭楼层建立父子关系。

## 父回复匹配规则

算法提前建立两个索引：

```text
用户名 + 楼层 → 当前页回复位置
用户名 → 遍历过程中该用户最近一次出现的位置
```

然后按照原始楼层顺序遍历每条回复，并采用以下优先级确定父回复：

1. 提取正文中的全部用户引用
2. 从最后一个引用开始，检查所有带楼层引用的“用户名 + 楼层”精确匹配
3. 任意精确引用命中后立即停止；精确关系始终高于模糊关系
4. 所有精确引用均失败且正文只提及一个用户时，匹配该用户最近的一条历史回复
5. 多人引用没有精确关系时保持为根节点，不猜测其中一个用户作为父节点
6. 找到第一个有效父回复后停止检查
7. 没有找到父回复时，将当前回复保留为根节点
8. 处理完当前回复后，更新该作者的最近回复位置

父节点必须位于当前回复之前。该限制保证生成结果不存在环，也不会把回复挂到未来楼层。

## 示例

### 精确匹配用户名和楼层

原始回复：

```text
1 楼 alice：第一条回复
2 楼 bob：另一条回复
3 楼 carol：@alice #1 我同意
```

楼中楼结果：

```text
1 楼 alice
└── 3 楼 carol

2 楼 bob
```

第 3 楼同时匹配 `alice` 和 `1`，因此精确挂到第 1 楼。

### 没有楼层时匹配最近回复

原始回复：

```text
1 楼 alice：第一条回复
2 楼 alice：补充说明
3 楼 bob：@alice 收到
```

楼中楼结果：

```text
1 楼 alice

2 楼 alice
└── 3 楼 bob
```

第 3 楼没有指定楼层，因此挂到 `alice` 在它之前最近出现的第 2 楼。

### 楼层与作者不一致

原始回复：

```text
1 楼 alice：第一条回复
2 楼 bob：第二条回复
3 楼 carol：@alice #2 继续讨论
```

`#2` 的实际作者是 `bob`，所以“`alice + 2`”精确匹配失败。算法随后回退到 `alice` 最近的回复，即第 1 楼：

```text
1 楼 alice
└── 3 楼 carol

2 楼 bob
```

### 多用户引用

原始回复：

```text
1 楼 alice：观点 A
2 楼 bob：观点 B
3 楼 carol：@alice #1 @bob #2 我更赞同后者
```

算法从最后一个引用开始检查，因此第 3 楼挂到第 2 楼：

```text
1 楼 alice

2 楼 bob
└── 3 楼 carol
```

一条回复只会有一个直接父节点，其他被提及用户不会产生额外副本。

多人引用没有任何精确关系时保持顶层：

```text
1 楼 alice：观点 A
2 楼 bob：观点 B
3 楼 carol：@alice @bob 大家说得都有道理
```

第 3 楼没有给出能够确认直接回复对象的楼层，因此不会猜测 `alice` 或 `bob` 为父节点。

如果多人引用中较早出现的引用能够精确匹配，而最后一个引用只能模糊匹配，算法会选择精确关系：

```text
1 楼 alice：观点 A
2 楼 bob：观点 B
3 楼 carol：@alice #1 @bob #999 补充
```

虽然 `bob` 是最后被提及的用户，但 `#999` 无法精确匹配；`alice #1` 可以精确匹配，因此第 3 楼挂到第 1 楼。

### 递归形成多层结构

原始回复：

```text
1 楼 alice：观点
2 楼 bob：@alice #1 提问
3 楼 carol：@bob #2 回答
```

楼中楼结果：

```text
1 楼 alice
└── 2 楼 bob
    └── 3 楼 carol
```

算法只计算每条回复的直接父节点，递归结构由节点之间的父子关系自然形成。

### 跨页引用

假设当前展示第 2 页，第 101 楼引用第 20 楼：

```text
101 楼 bob：@alice #20 补充一下
```

如果第 20 楼不在当前页，算法无法精确定位。如果当前页此前也没有 `alice` 的回复，第 101 楼会保留为根节点；如果当前页此前存在 `alice` 的回复，则会按最近回复规则回退。

## 复杂度

设当前页回复数量为 `n`，正文中提及的用户总数为 `m`：

- 时间复杂度：`O(n + m)`
- 空间复杂度：`O(n)`

索引使用 `Map`，父回复匹配不需要为每条回复向前扫描整个列表。

## 已知限制

- V2EX 没有提供父回复 ID，任何楼中楼关系都只能是推断结果
- 普通的用户提及可能被误判为直接回复
- 未指定楼层时，“最近一条同作者回复”不一定是用户真实回复的目标
- 多用户引用没有精确楼层关系时会保持顶层，可能无法还原回复者心中的直接对象
- 当前页无法可靠还原跨页父子关系
- 单用户引用中的独立 `#数字` 可能只是正文编号，而不是楼层
- 用户名匹配规则需要在 V2EX 用户名规范变化时同步更新

用户随时可以切回普通列表模式查看 V2EX 原始回复顺序，避免推断结果影响阅读。

## 后续优化方向

后续调整算法时，应优先补充覆盖目标场景的测试或固定回复样本，并记录规则变化。可考虑的方向包括：

- 仅将正文开头或引用区域中的 `@用户名` 视为强回复信号
- 区分 `@用户 #楼层`、单独 `@用户` 和正文中的普通 `#数字`
- 缓存已加载分页的最小回复索引，在不额外请求页面的前提下改进跨页匹配
- 增加最大视觉缩进限制和深层回复折叠，改善窄面板下的可读性

### TODO：回复关系置信度与来源

当前 `TopicReplyNode` 只保存 `children`，无法区分父子关系是精确匹配还是启发式推断。后续可为非根节点增加关系元数据：

```ts
interface ReplyRelation {
  /** 精确楼层、最近用户推断或不确定关系 */
  type: 'exact' | 'recent-user' | 'uncertain'
  /** 正文中被提及的用户名 */
  referencedUser?: string
  /** 正文中出现的楼层号 */
  referencedFloor?: string
}

interface TopicReplyNode extends TopicReply {
  relation?: ReplyRelation
  children: TopicReplyNode[]
}
```

建议按以下顺序实施：

1. 算法返回关系来源，但暂不改变现有嵌套结果
2. 为 `exact`、`recent-user` 和错误楼层补充单元测试与真实帖子测试
3. 在开发模式下统计各类关系数量，检查是否存在大量模糊匹配
4. 在 UI 中仅为 `recent-user` 或 `uncertain` 显示淡色“推测”或警告提示
5. 根据真实误判数据决定是否只嵌套达到置信度阈值的回复

该路线的目标是让用户能够区分确定关系和推测关系，而不是把启发式结果表现为 V2EX 提供的真实父回复数据。当前阶段暂不实现，避免过早增加树节点类型和界面复杂度。

修改匹配规则后，至少应人工验证：精确楼层、多次回复同一用户、多用户引用、递归嵌套、错误楼层、跨页引用，以及普通列表/楼中楼模式来回切换。
